Take your data out of Firestore — without taking your app offline.

Fireup reads a managed Firestore or Datastore export and imports it into a normalised PostgreSQL schema. It also serves the Firestore, Datastore and Firebase Auth APIs on one local port, so the code you are migrating keeps running against the SDKs it already uses.

Read the docs View the source 

$ fireup validate --backup-file ./export
read 2 input files · 13 records · 12/12 entities · 0 errors

$ fireup analyze --backup-file ./export --out ./schema
$ fireup import  --backup-file ./export --postgres-url $PG

$ fireup local --postgres-url $PG
firestore · datastore · auth  →  127.0.0.1:4589

One tool, two jobs

Import an export

Fireup parses a managed export the way the format is actually written — 32 KiB LevelDB blocks, masked CRC32C record checksums, fragment reassembly, and the legacy EntityProto payload with its proto2 groups — across every kind_*/output-N shard of the tree.

It then analyses the documents, normalises to 3NF, emits DDL for review, and imports the rows. Documents are keyed on their Datastore key_path, so a re-import updates rows instead of duplicating them.

Run the APIs locally

fireup local serves google.firestore.v1 and google.datastore.v1 over gRPC plus a subset of Identity Toolkit over REST — all on one port, which it demultiplexes by the HTTP/2 preface.

Documents live in memory or in PostgreSQL, behind one Store trait held to a single conformance suite, so both answer a query identically. An unreachable --postgres-url is a hard error, never a silent fall back to an empty store.

It talks to the SDKs you already have

Official Google and Firebase clients honour the emulator environment variables. Point them at Fireup and they speak to it instead of production — no shim, no fork, no patched client library.

Verified with Google's @google-cloud/firestore, firebase-admin 13 and the firebase client SDK 11 against both the in-memory and the PostgreSQL store. 

export FIRESTORE_EMULATOR_HOST=127.0.0.1:4589
export DATASTORE_EMULATOR_HOST=127.0.0.1:4589
export FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:4589

Fidelity, stated up front

An unsupported feature is an explicit error, never a wrong answer. Every refusal names the missing piece, so an SDK failure reads as a clear gap instead of a plausible-looking wrong result.

What Fireup serves and what it refuses
SurfaceStateDetail
Firestore v1 — documents, queries, transactions Served 12 of the 17 RPCs: reads, writes, RunQuery, atomic Commit with optimistic concurrency, BatchWrite, listings paged by resume token.
Datastore v1 Served Lookup, RunQuery, Commit, transactions, AllocateIds, ReserveIds. Kinds share the store with Firestore collections.
Firebase Auth / Identity Toolkit Subset Email+password, anonymous, custom token, refresh, lookup, update, delete and the project-scoped admin endpoints. Tokens are unsigned, as emulator-mode SDKs expect.
Realtime listeners, aggregations, PartitionQuery Refused Answered UNIMPLEMENTED with a message naming the gap.
Field transforms, cursors, collection-group queries Refused serverTimestamp() and increment() fail loudly rather than writing a wrong value.
Phone auth, MFA, federated providers, email link flows Refused Answered 501. Production key material is a non-goal.

Local development only. There is no auth on the data plane, tokens are unsigned, and passwords are hashed without a work factor. Anything that can reach the port can act as any account — which is why it binds to loopback and says so at startup.
